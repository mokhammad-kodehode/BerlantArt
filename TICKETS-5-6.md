## Как это устроено

Формат тот же, что в `TICKETS.md`: один тикет — один смысловой шаг
и один коммит, ревью — в чат до кода
([review.md](./.ai/rules/review.md)), закрытие — после трёх проверок
и просмотра глазами. Здесь это особенно важно: **каждый тикет ниже
задевает то, чего в проекте ещё не было** — новую зависимость
(Auth.js), границу «сервер — клиент» (форма загрузки, куда уходит
файл), логику, которую легко сломать незаметно (проверка файла,
подписанная ссылка, срок её действия). По критериям
[review.md](./.ai/rules/review.md) это большое ревью **на каждый
тикет**, без исключений — маленьких тут не будет.

## Что уже решено архитектурой, переигрывать не надо

Из [ARCHITECTURE.md](./ARCHITECTURE.md), раздел 4, и `ROADMAP.md`:

- **Хранилище — Cloudflare R2**, S3-совместимый API, нулевой egress.
- **Загрузка напрямую в R2 по подписанному URL** из браузера, не через
  свой сервер: на Vercel у Route Handler лимит тела ~4.5 МБ, а фото
  в хорошем качестве его пробивают. Сервер только подписывает адрес.
- **Таблицы `User` не будет.** Аккаунт один, логин и bcrypt-хеш пароля —
  в переменных окружения (`AUTH_ADMIN_EMAIL`, `AUTH_ADMIN_PASSWORD_HASH`).
  Понадобится второй аккаунт — заводим таблицу сразу, задним числом
  мигрировать дороже.
- **Auth.js (NextAuth v5), Credentials-провайдер, JWT-сессия.**
- Имена переменных уже зарезервированы в `.env.example`: `R2_ACCOUNT_ID`,
  `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET_NAME`,
  `NEXT_PUBLIC_R2_PUBLIC_URL`, `AUTH_SECRET`, `AUTH_ADMIN_EMAIL`,
  `AUTH_ADMIN_PASSWORD_HASH`.

## Разошлось с training-данными — прочитано из `node_modules/next/dist/docs/`

`AGENTS.md` требует это перед кодом, и здесь оно меняет план не косметически:

- **`middleware.ts` в Next 16 не существует — переименован в `proxy.ts`.**
  Файл лежит в корне проекта, и по умолчанию выполняется в Node.js-рантайме,
  а не в Edge, как раньше (`v16.0.0: Middleware is deprecated and renamed
to Proxy. Proxy defaults to the Node.js runtime`). Для нас это хорошая
  новость: рантайм больше не режет доступный набор Node-API.
- Next сам рекомендует для `proxy.ts` только **оптимистичную** проверку —
  по JWT-сессии в куке, без похода в базу («Proxy runs on every route,
  including prefetched routes… avoid database checks»). Значит:
  `proxy.ts` решает «есть валидная сессия — пускаем дальше», а не
  «пользователь действительно администратор» — это второй, надёжный
  рубеж внутри самих `/admin`-страниц через `auth()` из Auth.js.

## Развилки, которые беру на себя разумным выбором

По правилу из [workflow.md](./.ai/rules/workflow.md): выбираю очевидный
вариант, говорю вслух почему, продолжаю. Если не согласен — поправим,
пока ничего не написано.

1. **Порядок работы — не по номеру тикета, а по кратчайшему пути
   к «умею загружать картинку».** Список работ (`Э6-3`) и дашборд
   (`Э6-5`) — обвязка вокруг формы, а не то, что ты просил в первую
   очередь. Реальная зависимость только одна: форма (`Э6-2`) не
   заработает без входа (`Э6-1`) и без R2 (`Э5-1`). Смотреть
   `/admin/artworks/new` по прямой ссылке до появления таблицы,
   которая на неё ведёт, — приём, которым уже пользовались на этом
   проекте (страница работы проверялась по прямой ссылке до того, как
   плитки в галерее стали кликабельны).
2. **Существующие пять работ и их фото в `public/` не переезжают
   в R2.** `Image.url` — свободная строка: локальный путь и ключ объекта
   в хранилище работают вперемешку, разбирает их `imageUrl()`. Заставлять
   уже выложенные картины переезжать — работа без потребителя. Новые
   загрузки идут в R2, старые остаются как есть.
3. **Перетаскивание порядка изображений (drag-and-drop) — не в первой
   версии.** Это отдельная клиентская библиотека
   (`@dnd-kit` или подобная) ради удобства при 5–15 картинах на одну
   работу. По [code-style.md](./.ai/rules/code-style.md): «зависимость
   добавляется, только если без неё заметно хуже» — а без неё просто
   чуть менее удобно. Первая версия: числовое поле `order` и кнопки
   «выше / ниже». Понадобится реальное перетаскивание — заводим
   отдельным тикетом с отдельным ревью на новую зависимость.
4. **Ограничения на файл при загрузке** ([images.md](./.ai/rules/images.md)):
   `image/jpeg`, `image/png`, `image/webp`; не крупнее 10 МБ (с запасом
   над требуемыми 2000–2500px в хорошем JPEG-качестве). Проверяются
   дважды: на клиенте — для быстрой обратной связи, и на сервере при
   подписи URL — клиентской проверке верить нельзя.

   Уточнение по итогам Э5-1: тип файла удалось вшить в подпись, и хранилище
   само отвергает подмену. **Размер так закрепить нельзя** — при подписи
   проверяется только заявленный вес, поэтому Э6-2 обязан сверить
   фактический вес загруженного файла перед тем, как завести запись
   в базе, и удалить объект, если тот оказался больше.

## Э5-1 · Хранилище: клиент R2, подписанные ссылки, `next/image`

**Зачем.** Без этого загружать в форму (Э6-2) будет некуда — весь
смысл этапа 5 в одном тикете, дальше он используется, а не строится
заново.

**Что сделано.**

- `lib/r2.ts` — подпись разовых ссылок на загрузку через `aws4fetch`
  (1 пакет, 65 КБ; выбор и отвергнутый `@aws-sdk` — в
  [ARCHITECTURE.md](./ARCHITECTURE.md), раздел 2), сборка ключа объекта
  `artworks/<uuid>-<имя-латиницей>.<расширение>` и публичного адреса
  по ключу. Тип файла и заявленный размер проверяются на сервере.
- `lib/artworks.ts` — `imageUrl()`: в базе лежит ключ, а не полный адрес,
  и функция понимает оба формата. `primaryImageUrl()` и страница работы
  переведены на неё.
- `next.config.ts` — `images.remotePatterns` на публичный домен бакета;
  правило добавляется, только когда домен задан.
- `lib/env.ts` — схема переменных R2, проверяется **лениво**, при первом
  обращении к хранилищу.
- `vitest` + `lib/r2.test.ts` — шесть тестов на чистые функции: транслит
  имени, расширение из типа файла, попытка уйти вверх по дереву
  (`../../secret.png`), сборка адреса.

**Три развилки решены иначе, чем планировалось** (по итогам ревью):
Server Action наружу не выставлен и переехал в Э6-2 (до Э6-1 это было бы
разрешение писать в бакет кому угодно); переменные R2 не стали
обязательными при сборке; в базе хранится ключ, а не полный адрес.
Причины — в `ARCHITECTURE.md`.

**Файлы.** `lib/r2.ts`, `lib/r2.test.ts`, `lib/env.ts`, `lib/artworks.ts`,
`app/gallery/[id]/page.tsx`, `next.config.ts`, `vitest.config.ts`,
`.env.example`, `package.json`.

**Проверено живьём** (скрипт мимо браузера, приём из
[workflow.md](./.ai/rules/workflow.md)): ссылка подписывается, файл
кладётся по ней в бакет (200), скачивается обратно байт в байт, читается
по публичному адресу без ключей (`content-type: image/jpeg`), тестовый
объект удаляется (204). Отказы тоже проверены: чужой `Content-Type` — 403,
файл 11 МБ и PDF — отказ до обращения к сети.

**Живая проверка поймала ошибку, которую не поймали ни типы, ни тесты:**
без `allHeaders: true` подпись не покрывала `Content-Type`, и ссылка,
выданная под JPEG, приняла `application/zip` с ответом 200. Исправлено,
причина записана в коде рядом со строкой.

**Найдено по пути, вне тикета:**

- у `next/image` в Next 16 свойство `priority` объявлено устаревшим
  в пользу `preload` — у нас оно в `app/gallery/[id]/page.tsx`
  и `components/ui/ArtworkImage.tsx`;
- `@types/node` в проекте от Node 20, а машина работает на Node 26;
- поле `Image.url` честнее назвать `path` — отложено до ближайшей
  миграции;
- к Э6-2 понадобится настроить **CORS на бакете**: файл начнёт класть
  браузер, а не скрипт.

## Э6-1 · Вход в админку: Auth.js, `proxy.ts`, защита `/admin`

**Зачем.** Без входа `/admin` — публичная страница, что бы на ней
ни было.

**Что делаю.**

- Auth.js (NextAuth v5), Credentials-провайдер: сверяет
  `AUTH_ADMIN_EMAIL` и введённый пароль (`bcrypt.compare` с
  `AUTH_ADMIN_PASSWORD_HASH`) — без похода в базу, аккаунт один
  и он в переменных окружения. Сессия — JWT, без БД под неё.
- `proxy.ts` в корне проекта (**не `middleware.ts`** — в Next 16 это
  устаревшее имя): оптимистичная проверка по куке сессии, редирект
  на `/admin/login` для всего под `/admin`, кроме самой страницы
  входа. Проверку «сессия не поддельная» это не делает — она уже
  сделана Auth.js при выдаче JWT.
- `/admin/login` — форма логина, без индексации
  ([security.md](./.ai/rules/security.md), как `/styleguide`).
- Скрипт `scripts/hash-password.ts` (или похожее имя) — генерирует
  bcrypt-хеш пароля, который ты придумаешь; кладу в проект, не в
  переписку ([security.md](./.ai/rules/security.md): пароль
  в чат не присылать).
- `lib/env.ts`: `AUTH_SECRET`, `AUTH_ADMIN_EMAIL`,
  `AUTH_ADMIN_PASSWORD_HASH` — из закомментированных в обязательные.

**Файлы.** `lib/auth.ts` (конфигурация Auth.js), `proxy.ts`,
`app/admin/login/page.tsx`, `scripts/hash-password.ts`, `lib/env.ts`,
`package.json` (новая зависимость: `next-auth@5`, `bcryptjs`).

**Готово, когда.** Заход на `/admin/artworks` без сессии уводит на
`/admin/login`; неверный пароль — понятная ошибка на форме; верный —
пускает и сессия переживает перезагрузку страницы. Три проверки чисто.

**Проверить не удастся без.** Пароля от тебя. Пока его нет — тикет
проверяется временным паролем и остаётся сказанным прямо: «вход
работает, но пароль временный, замени на свой».

## Э6-2 · Форма работы: создание, редактирование, загрузка фото

**Зачем.** Это и есть то, что ты попросил — «загружать картинки».
Самый большой тикет пула, дальше всё остальное вокруг него.

**Что делаю.**

- `app/admin/artworks/new/page.tsx` и `app/admin/artworks/[id]/page.tsx` —
  одна форма на оба случая: без `id` создаёт, с `id` редактирует.
- Поля по схеме `Artwork`: название, описание, категория, техника,
  размеры, год, цена, статус, `featured` — валидация Zod на входе
  Server Action ([architecture.md](./.ai/rules/architecture.md):
  данные формы проверяются один раз, на входе).
- Загрузка изображений: клиентский компонент — выбор файла →
  запрос подписанного URL (Э5-1) → `PUT` файла напрямую в R2 из
  браузера → по успеху сохраняется `Image` в базе с этим URL.
  Прогресс и ошибку сети показывает пользователю, а не проглатывает.
- Порядок изображений — числовое поле плюс кнопки «выше / ниже»
  (см. развилку №3 выше, не drag-and-drop). Выбор `isPrimary` —
  переключатель на одном из изображений.
- Удаление одного изображения из работы — с чисткой объекта в R2
  (не только записи в базе, иначе в бакете копится мусор, за который
  платим).
- Server Action завершается `revalidatePath("/gallery")` и
  `revalidatePath("/gallery/[id]", "page")` — иначе публичные страницы
  останутся со старыми данными до истечения `revalidate = 300`.

**Файлы.** `app/admin/artworks/new/page.tsx`,
`app/admin/artworks/[id]/page.tsx`, форма и загрузчик в
`components/admin/`, Server Actions в `lib/actions/artworks.ts` (или
похожее место — решается на ревью тикета).

**Готово, когда.** Новая работа создаётся с нуля, минимум с одним
изображением; существующая редактируется, включая замену и удаление
фото; изменение видно на публичной странице сразу после сохранения
(`revalidatePath` сработал); загрузка файла не того типа или крупнее
лимита отклоняется с понятным текстом, а не тихо.

## Э6-4 · Удаление работы с подтверждением, чистка R2

**Зачем.** Работа могла быть добавлена по ошибке или снята с продажи

**Файлы.** Кнопка и диалог — в `components/admin/`, Server Action —
рядом с остальными в `lib/actions/artworks.ts`.

**Готово, когда.** Удалённая работа пропадает из галереи сразу;
в бакете R2 не остаётся её файлов — проверяется списком объектов
по префиксу `artworks/<id>/`.

## Э6-5 · `/admin` — дашборд: счётчики, последние работы

**Зачем.** Первый экран админки — по нему видно состояние коллекции,
