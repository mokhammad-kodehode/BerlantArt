# План работ: сайт-портфолио художницы

Составлен: 2026-08-18. Архитектура — см. [ARCHITECTURE.md](./ARCHITECTURE.md).

## Как читать план

9 этапов, идут по зависимостям. У каждого: **цель**, **что делаю**, **выход** (что готово по завершении), **нужно от тебя** (если этап заблокирован внешними данными).

Ключевое про порядок: этапы 1–2 не требуют вообще ничего внешнего — их можно начинать сразу, пока ты параллельно заводишь аккаунты для этапа 0. Первая реальная блокировка — этап 3 (нужен Supabase).

```
Э0 (аккаунты, контент) ──────────┐
                                 ├──> Э3 (БД) ──> Э4 (страницы) ──> Э5 (R2) ──> Э6 (админка) ──> Э7 (полировка) ──> Э8 (деплой) ──> Э9 (контент)
Э1 (каркас) ──> Э2 (дизайн) ─────┘
```

## Этап 0 — Подготовка: аккаунты, контент, решения

**Цель:** снять все внешние блокировки до того, как они остановят работу.

### Нужно от тебя — аккаунты

| Сервис        | Что нужно получить                                                        | Куда пойдёт |
| ------------- | ------------------------------------------------------------------------- | ----------- |
| Supabase      | `DATABASE_URL` (pooler, порт 6543) и `DIRECT_URL` (прямой, 5432)          | этап 3      |
| Cloudflare R2 | bucket, Access Key ID + Secret, endpoint аккаунта, публичный домен бакета | этап 5      |
| Vercel        | аккаунт, привязанный к GitHub                                             | этап 8      |
| GitHub        | пустой приватный репозиторий                                              | этап 1      |

Секреты присылать в чат не нужно — я подготовлю `.env.example`, ты впишешь значения локально сам.

### Нужно от тебя — контент

- Текст «о художнице»: биография, путь, вехи, про технику.
- Портрет художницы (для `/about`).
- 8–15 работ для старта: фото + название, категория, техника, размеры, год, цена, статус.
- Контакты: номер WhatsApp в международном формате, e-mail.

### Решения, которые нужно принять

1. **Язык сайта.** Пока исхожу из: **только русский, без i18n-инфраструктуры**. Если нужен английский (иностранные покупатели) — говори до этапа 4, задним числом это переделка всех страниц.
2. **Домен.** Свой или временный `*.vercel.app` на старте.
3. **Цены.** Показываем публично или «цена по запросу»? Влияет на карточку и фильтр по цене.

**Выход:** заполненный `.env.local`, папка с исходниками контента, три решения приняты.

## Этап 1 — Каркас проекта

**Цель:** пустой, но правильно собранный и запускающийся проект.

**Что делаю:**

- `create-next-app`: App Router, TypeScript, Tailwind, ESLint, алиас `@/*`.
- `git init`, `.gitignore`, первый коммит, связка с твоим GitHub-репо.
- Prettier + `prettier-plugin-tailwindcss`, единый конфиг форматирования.
- Структура папок: `app/`, `components/ui/`, `components/layout/`, `lib/`, `prisma/`, `public/`.
- Валидация env через Zod (`lib/env.ts`) — падаем на старте при отсутствующей переменной, а не в рантайме на проде.
- `.env.example` с полным списком переменных.

**Выход:** `npm run dev` поднимает пустую страницу, линт и сборка проходят, код в git.

**Нужно от тебя:** ничего (URL репозитория — когда будет).

## Этап 2 — Дизайн-система

**Цель:** визуальный язык зафиксирован в коде, дальше страницы собираются из готовых блоков.

**Что делаю:**

- Токены в Tailwind: кремовый фон, охра/сиена акценты, нейтрали, тени.
- Шрифты через `next/font/google`: Fraunces (заголовки), Work Sans (текст) — самохостинг, без внешних запросов.
- Типографическая шкала: размеры, интерлиньяж, вертикальный ритм.
- Фирменные приёмы: бумажная текстура (SVG-шум или тайл), рисованные разделители секций (inline SVG).
- Примитивы: `Container`, `Section`, `Heading`, `Button`, `Divider`, `Badge` (для статуса работы).
- Каркас: `Header` с навигацией, `Footer` с контактами, мобильное меню.
- Страница `/styleguide` — все компоненты на одном экране, чтобы визуально сверяться (в проде закрыта).

**Выход:** сверстанные хедер/футер, работающий стайлгайд, макеты главной и `/about` переводимы в код без изобретения новых стилей.

**Нужно от тебя:** ничего.

## Этап 3 — Данные

**Цель:** схема БД, миграции, тестовые данные, слой запросов.

**Что делаю:**

- Prisma schema: `Artwork` (title, description, category, technique, dimensions, year, price, status), `Image` (artworkId, url, alt, isPrimary, order), enum `ArtworkStatus`.
- Подключение к Supabase: `DATABASE_URL` через pooler для приложения, `DIRECT_URL` для миграций (иначе миграции на serverless ломаются).
- Индексы под фильтры: `category`, `technique`, `status`, `price`.
- Первая миграция + `seed.ts` с 10–12 демо-работами и картинками-плейсхолдерами.
- Singleton Prisma-клиента (`lib/db.ts`) — иначе в dev-режиме утекают подключения.
- Слой запросов `lib/artworks.ts`: `getArtworks(filters)`, `getArtworkById`, `getFeatured` — вся фильтрация через Prisma `where` на сервере.

**Выход:** база поднята, `npx prisma studio` показывает демо-работы, функции выборки готовы.

**Нужно от тебя:** `DATABASE_URL` и `DIRECT_URL` из Supabase (этап 0).

## Этап 4 — Публичные страницы

**Цель:** весь публичный сайт работает на реальных данных из БД.

**Что делаю, по порядку:**

1. **`/`** — hero с главной картиной, превью-галерея (6–8 работ), тизер «о художнице» со ссылкой на `/about`, CTA. Минимум текста, визуал в приоритете.
2. **`/about`** — полная история, вехи, техника, портрет.
3. **`/gallery`** — сетка работ + фильтры (категория, техника, цена, статус). Фильтры через `searchParams`, состояние в URL — ссылку на отфильтрованную выборку можно скинуть в мессенджер; серверный рендер, без клиентской библиотеки фильтров.
4. **`/gallery/[id]`** — крупное изображение + миниатюры остальных, все атрибуты работы, кнопки «Написать в WhatsApp» и «Написать на почту» с предзаполненным текстом (название работы подставляется), блок «другие работы».
5. **`/contact`** — **точка решения**: если после готовности карточки работы видно, что контактов в футере хватает, страницу не делаем. Решаем по факту, не заранее.

Плюс на каждой странице: состояния loading/empty/404, `generateMetadata`.

**Выход:** публичная часть сайта проходится целиком, данные живые.

**Нужно от тебя:** тексты и решение по ценам (этап 0). Пока текстов нет — верстаю на рыбе, подмена текста потом дешёвая.

## Этап 5 — Изображения и Cloudflare R2

**Цель:** реальные фото картин, быстрые и оптимизированные.

**Что делаю:**

- S3-клиент к R2 (`lib/r2.ts`), проверка доступа.
- Загрузка **напрямую в R2 по presigned URL** из браузера, не через свой сервер: на Vercel у route handler лимит тела ~4.5 МБ, а фото картин в хорошем качестве его пробивают. Сервер только подписывает URL и потом сохраняет запись в БД.
- Валидация на подписи: тип файла, размер, генерация ключа объекта.
- `next/image` + `remotePatterns` на публичный домен бакета, правильные `sizes`, `priority` для hero.
- Blur-плейсхолдеры, чтобы галерея не «прыгала» при загрузке.
- Удаление объекта из R2 при удалении работы — чтобы не копился мусор, за который платим.

**Выход:** изображения лежат в R2, отдаются через CDN, галерея грузится быстро.

**Нужно от тебя:** ключи R2 и публичный домен бакета (этап 0).

## Этап 6 — Аутентификация и админка

**Цель:** ты можешь управлять сайтом без моего участия.

**Что делаю:**

- Auth.js (NextAuth v5), Credentials-провайдер, JWT-сессия.
- **Без таблицы пользователей**: логин и bcrypt-хеш пароля в env-переменных. Аккаунт один, таблица `User` тут — лишняя сущность и лишняя поверхность атаки. (Если захочешь несколько аккаунтов позже — скажи, тогда заводим таблицу сразу, потом мигрировать дороже.)
- Middleware: всё под `/admin` закрыто, редирект на логин.
- `/admin` — дашборд: счётчики по статусам, последние работы.
- `/admin/artworks` — таблица со всеми работами, поиск, фильтр по статусу, быстрая смена статуса.
- `/admin/artworks/new` и `/admin/artworks/[id]` — форма: все поля, валидация Zod, мультизагрузка изображений, перетаскивание порядка, выбор `isPrimary`, удаление изображения.
- Удаление работы с подтверждением.
- Server Actions + `revalidatePath`, чтобы публичные страницы обновлялись сразу после правки.

**Выход:** полный цикл «добавил работу → она на сайте» проходится через админку.

**Нужно от тебя:** придумать пароль админа (хеш сгенерируешь скриптом, который я положу в проект).

## Этап 7 — Полировка, SEO, доступность

**Цель:** сайт не просто работает, а выглядит и индексируется как надо.

**Что делаю:**

- Адаптив: проверка на 375 / 768 / 1280 / 1920, отдельно — галерея и карточка.
- Доступность: alt у всех изображений, фокус-стили, контраст, навигация с клавиатуры, семантика.
- SEO: метаданные на всех страницах, Open Graph (превью в мессенджерах — критично, ссылки будут кидать в WhatsApp), `sitemap.ts`, `robots.ts`, JSON-LD разметка `VisualArtwork` для карточек.
- Производительность: Lighthouse, размеры изображений, шрифты, бандл.
- Обработка ошибок: `error.tsx`, `not-found.tsx`, поведение при недоступной БД.

**Выход:** Lighthouse в зелёной зоне, ссылка красиво разворачивается в мессенджерах.

**Нужно от тебя:** ничего.

## Этап 8 — Деплой

**Цель:** сайт в интернете.

**Что делаю:**

- Проект на Vercel из GitHub-репо, env-переменные в трёх окружениях.
- Прод-миграция Prisma, `postinstall` с `prisma generate`.
- CORS на бакете R2 под прод-домен.
- Домен + SSL.
- Смоук-тест на проде: галерея, фильтры, карточка, WhatsApp-ссылка с телефона, вход в админку, загрузка изображения.

**Выход:** рабочий сайт на боевом домене.

**Нужно от тебя:** аккаунт Vercel, домен, доступ к DNS.

## Этап 9 — Наполнение и передача

**Цель:** сайт с реальными работами, ты умеешь им пользоваться.

**Что делаю:**

- Заливаем реальные работы через админку (первые несколько — вместе, дальше сама/сам).
- Удаляем демо-данные.
- Короткая инструкция в `README.md`: как добавить работу, как поменять статус на «продано», как поменять текст на главной.

**Выход:** сайт готов к тому, чтобы кидать ссылку клиентам.
